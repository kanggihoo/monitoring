## 0. 서비스의 위치

```
폐장 16:40  백엔드가 daily_settlements 커밋
     ↓      DailySettlementFinalizedEvent
백엔드 ──(POST /api/ai/reports/daily, X-Internal-Api-Key)──▶ AI
     ↓      payload → 조건 벡터 → 블록 선택(+ 헤드라인 생성) → 문장
백엔드 ◀──(계좌별 문구)── AI
     ↓      daily_report_texts 저장
17:00 정산 발표부터 화면에 나간다
```

세 가지가 이 서비스의 성격을 정한다.

1. **내부 서비스다.** 브라우저가 직접 호출하지 않는다. CORS 를 열지 않고 사용자 세션·JWT 를
   검증하지 않는다. 인증은 백엔드와 나눠 갖는 공유 시크릿 하나다.
2. **DB 를 읽지 않는다.** 백엔드가 추려 보낸 요청 본문만 본다
   ([ADR-0002](../../ai/docs/adr/0002-backend-sends-preprocessed-payload.md)).
   집계는 백엔드, 판정은 AI 다.
3. **없어도 게임은 멈추지 않는다.** 응답을 못 받으면 백엔드가 문구 자리를 비운 채 리포트를 연다
   (`rpt.md` — `commentary` 는 `null` 일 수 있다).

호출 시점은 둘뿐이다. 일일은 일차마다 폐장 정산 뒤 한 번, 시즌은 3일차 정산 뒤 한 번.

## 1. 엔드포인트

| 메서드 | 경로 | 인증 | 용도 |
|---|---|---|---|
| GET | `/health` | 없음 | Liveness. 컨테이너 healthcheck·로드밸런서가 찌른다. 응답에 `env`·`version` |
| GET | `/api/ai/health/internal` | 내부 키 | 양쪽 키가 맞는지만 확인. 불일치면 401 |
| POST | `/api/ai/reports/daily` | 내부 키 | 일일 매매 코멘터리. 일차마다 한 번, 전원분 |
| POST | `/api/ai/reports/season` | 내부 키 | 시즌 총평·투자자 유형. 3일차 뒤 한 번, 전원분 |

도메인 엔드포인트는 전부 `/api/ai` 아래에 둔다. `GET /health` 만 접두사 밖에 있다 — 헬스체크는
API 버저닝·접두사 정책과 분리한다.

> **비고** — `/docs` 는 현재 모든 환경에서 열려 있다. 공개 범위는 미결이다 (11절).

## 2. 인증과 응답 규약

### 2.1 인증

헤더 `X-Internal-Api-Key` 하나다. 값은 양쪽 환경변수(`AI_INTERNAL_API_KEY`)로 나눠 갖는다.

1. 비교는 `secrets.compare_digest` 로 한다 (타이밍 공격 회피). 키 값은 로그에 남기지 않는다.
2. 키가 비어 있으면 검증을 건너뛴다. **`AI_ENV=local` 에서만 가능하다** — `dev`·`prod` 는
   키가 없으면 기동 자체가 실패한다. 조용히 열린 채 배포되는 것을 막는다.
3. 누락·불일치는 401 이다. 이 서비스의 401 은 사용자 인증이 아니라 **내부 호출 키**를 뜻한다.

### 2.2 응답 봉투

백엔드 `code.md` §6 과 같은 모양이다. JSON 키는 camelCase 로 낸다.

| 성공 | `{ success: true, status, message, data, timestamp }` |
|---|---|
| 실패 | `{ success: false, status, message, errors[], path, timestamp }` |

백엔드는 `data` 만 벗겨 `AiDailyReportResponse`·`AiSeasonReportResponse` 로 읽는다.

### 2.3 상태 코드

| 코드 | 언제 | 응답 |
|---|---|---|
| 400 | 요청 본문 검증 실패 | `errors[]` 에 `{ field, rejectedValue, reason }` |
| 401 | 내부 호출 키 누락·불일치 | — |
| 500 | 블록 정의·치환 오류, 예상 못한 예외 | 내부 구현 정보를 응답에 싣지 않는다 |
| 502 | 외부 모델·게이트웨이 연동 실패 | 리포트 발급 경로에서는 올라오지 않는다 (6.3) |
| 503 | 일시적 인프라 장애 | 애플리케이션 버그(500)와 구분한다 |

라우터 안에서 `try/except` 로 응답을 만들지 않는다. 예외를 던지고 전역 핸들러가 한 곳에서 변환한다.

## 3. 일일 매매 코멘터리 — `POST /api/ai/reports/daily`

### 3.1 받는 것

`DailyReportRequest` (`ai/app/schemas/inbound.py` 가 정본). 한 요청에 그 일차 전원분이 담긴다.

| 값 | 의미 |
|---|---|
| `seasonId` · `seasonDay` | 시즌과 일차 |
| `indexReturn` | 지수 대리 종목의 그 일차 구간 수익률(%). 편성값 `app.ai.index-proxy-symbol` (기본 `NQX`) |
| `accounts[].dailyReturn` | 당일 수익률(%) — `daily_settlements.daily_return` |
| `accounts[].executionCount` | 당일 체결 건수 |
| `accounts[].patternTags[]` | 백엔드가 판정한 태그 최대 6건. 종목명·방향·게임 연월·변화율이 함께 온다 |
| `accounts[].highlights[]` | 실현 손익 기준 최고·최악 매도 |
| `accounts[].metrics` | 승률·집중도·체결 순위 등 숫자 줄의 재료 (건수·금액으로 받는다) |

**거래가 0건인 계좌도 온다.** 태그와 하이라이트가 빈 배열이면 AI 가 관망으로 판정한다. 걸러내면
그 사용자만 리포트가 빈다.

**체결 원본을 받지 않는다.** 문장에 닿는 것은 계좌당 3~8건이고 그것이 무엇인지는 폐장 집계가
이미 가려 두었다. 계좌당 payload 가 23KB → 350~650B 로 줄었다.

### 3.2 판정 — 조건 벡터

받은 값을 세 가지로 줄인다. 임계값은 `ai/app/services/extract.py` 의 `THRESHOLDS` 한 곳에 있다.

**`vsIndex` — 시장 대비 위치**

| 조건 | 값 |
|---|---|
| 당일 수익률 − 지수 수익률 > +0.5%p | `ABOVE` |
| −0.5%p ~ +0.5%p | `SIMILAR` |
| < −0.5%p | `BELOW` |

**`mainMistake` — 그날 가장 아쉬웠던 점**

1. 태그 중 `PEAK_BUY`(고점 매수)·`BOTTOM_SELL`(저점 매도)의 건수를 센다. 최다가 이긴다.
2. 동수면 `PEAK_BUY` > `BOTTOM_SELL` > `OVERTRADE` > `QUIET` 순서로 자른다.
   순서를 고정하지 않으면 같은 입력에 다른 리포트가 나온다.
3. 해당 태그가 없고 체결이 15건 초과면 `OVERTRADE`, 그 외에는 `QUIET`.

잘한 태그(저점 매수·고점 매도)는 세지 않는다. 이름 그대로 아쉬웠던 쪽을 고르는 자리다.

**`scenes` — 오늘의 세 장면 (0~3개)**

1. 태그가 먼저다. **변화율 절대값 내림차순**, 같으면 받은 순서.
2. 셋이 차지 않으면 최고·최악 매도로 채운다. 태그는 ±10% 를 넘긴 거래에만 붙어서, 크게 벌거나
   잃고도 태그가 하나도 없는 날이 있다.
3. 손익 부호가 역할과 맞을 때만 쓴다 — 손실만 난 날의 '최고'는 덜 잃은 거래일 뿐이라 잘한
   거래로 부르면 문장이 거짓이 된다.
4. 게임 연월·종목·방향이 같으면 같은 체결로 보고 중복을 뺀다 (매도가 한 건인 날은 최고와 최악이
   같은 체결을 가리킨다).

태그 이름은 백엔드와 AI 가 다르고 매핑이 한 곳(`TAG_FROM_PATTERN_KIND`)에 있다. **모르는 이름은
조용히 버린다** — 백엔드가 태그를 늘려도 AI 가 깨지지 않는다.

| 백엔드 `kind` | 뜻 | AI 쪽 이름 |
|---|---|---|
| `PANIC_BUY_HIGH` | 매수 후 −10% 이상 | `PEAK_BUY` |
| `PANIC_SELL_LOW` | 매도 후 +10% 이상 | `BOTTOM_SELL` |
| `LUCKY_BUY_LOW` | 매수 후 +10% 이상 | `BOTTOM_BUY` |
| `LUCKY_SELL_HIGH` | 매도 후 −10% 이상 | `PEAK_SELL` |
| (태그 없음, 하이라이트로 채움) | 그날 최고·최악 매도 | `BEST_TRADE` · `WORST_TRADE` |

### 3.3 내보내는 것

계좌마다 셋이다.

| 필드 | 내용 |
|---|---|
| `headline` | 리포트 맨 위 한 문장. LLM 생성 또는 블록 문장 (6절) |
| `sceneAliases` | 장면 수만큼의 별칭 (0~3개). 예: "꼭대기 수집", "오늘의 유일한 실수" |
| `blockIds` | 쓴 블록 ID. 화면에 나가지 않고 **다음 일차의 변주 회피**에 쓰인다 |

지표 칩(승률·집중도·수수료 등)은 백엔드 값이라 AI 응답에 담지 않는다.

**요청한 계좌가 다 오지 않을 수 있다.** 한 계좌의 조립이 실패해도 나머지를 보낸다 (7절).

## 4. 시즌 리포트 — `POST /api/ai/reports/season`

### 4.1 받는 것

`SeasonReportRequest`. **한 요청에 전원분이 들어와야 한다** — 판정에 "체결 수 상위·하위 10%",
"평균 보유 상위 10%" 조건이 있어 배치 안의 분포로 백분위를 잡는다. 나눠 보내면 배치마다 기준이
달라져 같은 사용자가 다른 유형을 받는다.

**비율이 아니라 건수·금액으로 받는다.** `GROUP BY` + `COUNT` 가 SQL 이 자연스럽게 내는 모양이고,
비율을 받으면 분모의 정의가 백엔드 배포에 굳는다. 나눗셈은 AI 쪽 한 함수
(`inbound.to_behavior_profile`)에 모여 있다.

### 4.2 상대 가격 위치 R

게임에 고가·저가가 없다 (단일 가격 모델, 기획서 4.1.3). 그래서 **창 20거래일(체결일 전후) 종가의
최고·최저**로 잡는다.

```
R = (체결가 − 창 최저) / (창 최고 − 창 최저)
```

- 창 최고 = 최저면 그 체결은 어느 조건에도 세지 않는다 (분모 0)
- 창이 달력 밖으로 나가면 있는 만큼만 쓴다
- `보유 기간` = FIFO 로 짝지은 게임 거래일 수, `수익률` = 취득 원가 대비 %

'금방 팔았다'의 기준이 **보유 20거래일**인 이유는 시간 축 때문이다. 게임 1거래일이 실시간 약 36초라
2일로 잡으면 실시간 70초가 되어 실투자의 '조급한 익절'과 다른 것을 재게 된다.

### 4.3 세어 보내는 항목

| 필드 | 세는 것 |
|---|---|
| `buyCount` · `sellCount` | 시즌 전체 매수·매도 체결 건수 |
| `fomoBuyCount` | R ≥ 0.85 인 매수 |
| `bottomSnipeBuyCount` | R ≤ 0.15 인 매수 |
| `peakSellWinCount` | R ≥ 0.85 이고 실현 손익 양수인 매도 |
| `panicBottomSellCount` | R ≤ 0.15 이고 수익률 ≤ −5% 인 매도 |
| `quickProfitCount` | 보유 ≤ 20거래일, 수익률 +1%~+3% 인 매도 |
| `quickStopCount` | 보유 ≤ 20거래일, 수익률 −5%~−3% 인 매도 |
| `winCount` | 실현 손익 양수인 매도 건수 |
| `krwCash` · `totalValuationKrw` | 시즌 종료 시점 원화 현금과 총 평가액 (관망 판정) |
| `holdingDaysSum` · `closedPositionCount` | 청산 포지션의 보유 일수 합과 건수 |
| `maxDrawdown` · `turnover` · `totalFeeKrw` | 시즌 지표 |
| `finalRank` · `totalParticipants` | 확정 순위와 그 분모 |
| `returnRate` | `season_reports.final_return` 에 서식만 입힌 문자열 (예: `+38.2%`) |

`holdingDaysSum`·`closedPositionCount` 는 **어려우면 0으로 두고 보내도 된다.** 0이면 평균 보유
일수를 0으로 보고 다른 지표로 유형을 가린다.

### 4.4 투자자 유형 9종 + 유보

> **이 절은 옛 설계다.** 9종 임계값 판정은 사라졌고, 지금은 상황형 5문항과 행동 5항목을
> 같은 5단계 척도로 옮겨 대조한다 — [`AI_투자자유형_분석.md`](specs/AI_투자자유형_분석.md) 가 정본이다.
> 그 작업이 끝날 때까지는 아래가 현재 동작이다.

판정 순서는 위에서 아래다 (`TYPE_PRIORITY`). 조건이 겹치는 계좌가 많아 순서를 고정하지 않으면
같은 입력에 다른 유형이 나온다.

| # | 유형 | 코드 | 조건 |
|---|---|---|---|
| 1 | 지켜보는 사람 | `OBSERVER` | 체결 수 하위 10% **이면서** 현금 비중 ≥ 50% |
| 2 | 쉬지 않는 사람 | `OVERTRADER` | 체결 수 상위 10% + 청산 ≥ 10건 + 평균 보유 ≤ 20거래일 |
| 3 | 오래 버티는 사람 | `DIAMOND_HANDS` | 평균 보유 상위 10% + 청산 1건 이상 |
| 4 | 내려가면 파는 사람 | `PANIC_BOTTOM_SELLER` | 아래 '최다 조건' 규칙 — `panicBottomSellCount / sellCount` |
| 5 | 고점에서 파는 사람 | `PEAK_SELLER` | `peakSellWinCount / sellCount` |
| 6 | 빨리 끊는 사람 | `QUICK_STOP_LOSSER` | `quickStopCount / sellCount` |
| 7 | 빨리 챙기는 사람 | `QUICK_PROFIT_TAKER` | `quickProfitCount / sellCount` |
| 8 | 오르면 사는 사람 | `FOMO_BUYER` | `fomoBuyCount / buyCount` |
| 9 | 떨어지면 사는 사람 | `BOTTOM_SNIPER` | `bottomSnipeBuyCount / buyCount` |
| — | 아직 그리는 중 (유보) | `UNDETERMINED` | 어느 조건도 넘지 못한 상태 |

4~9 의 '최다 조건' 규칙은 이렇다.

1. 분모(매수 또는 매도 건수)가 **5건 미만이면 그 조건을 건너뛴다.** 매도 2건 중 1건이 50% 가
   되는 것을 막는다.
2. 여섯 조건의 비중 중 **가장 큰 것**을 고른다. 그 비중이 **10% 미만이면 유보**다.
3. 동점이면 위 표의 순서가 이긴다.

> **비고** — 승인된 기준은 "조건 비중 40% 이상"이었다. 규칙 기반 목업 60명으로 재 보니 실제 비중이
> 0.03~0.20 에 머물러 **86.7% 가 유보로 떨어졌다.** 창 상단·하단 15% 에 체결이 40% 나 몰리는 일은
> 드물다. 그래서 절대값 대신 최다 조건을 쓰고 최소선만 10% 로 둔다 (유보 5.0%).

**유보를 특정 유형에 몰아주지 않는다.** 조건을 못 넘은 사람에게 유형을 붙이면 그 사람 수가 가장
많아지고 문장도 거짓이 된다.

### 4.5 `axis` — 이번 장에서 통했는가

`WORKED` / `BACKFIRED` 둘이다.

1. **최종 수익률의 부호가 먼저다.** 양수면 `WORKED`, 음수면 `BACKFIRED`.
2. 수익률이 정확히 0이거나 읽히지 않을 때만 승률로 가른다 (매도 5건 이상, 승률 ≥ 50%).

부호를 먼저 보는 이유는 같은 문장 안에 `{returnRate}` 가 함께 실리기 때문이다. 수익으로 끝난
사람에게 '어긋났다' 쪽 문장을 주면 한 문장 안에서 앞뒤가 맞지 않는다.

### 4.6 문장 재료는 AI 가 유도한다

예전 계약의 `patternCount`·`hitCount`·`gapRate` 는 순환이라 빠졌다 — 블록 문안("추격 매수
{count}회 중")이 뜻하는 것은 *판정된 유형의* 특징 거래 횟수인데, 유형은 AI 가 정하므로 백엔드가
미리 셀 수 없다.

| 치환값 | 만드는 방법 |
|---|---|
| `{count}` | 판정된 유형을 만든 조건의 건수 (`PATTERN_COUNT_FIELD`) |
| `{winCount}` | `winCount` 그대로 |
| `{returnRate}` | `returnRate` 그대로 (서식까지 백엔드 값) |
| `{rankRate}` | `finalRank / totalParticipants` 를 **올림**해 `상위 12%`. 1등을 '상위 0%'라 부르지 않기 위해서다. 순위를 모르면 빈 문자열이고 그 문장을 쓰는 블록이 후보에서 빠진다 |

### 4.7 내보내는 것

| 필드 | 내용 |
|---|---|
| `investorType` | 유형 코드 (위 10종 중 하나). 백엔드가 `season_report_texts.investor_type` 에 저장 |
| `typeName` | 유형 카드 이름 (예: "떨어지면 사는 사람") |
| `typeDescription` | 유형 카드 본문 |
| `verdict` | 시즌 국면 문장 + 작동·역작동 문장을 이어 붙인 총평 |
| `blockIds` | 쓴 블록 ID 셋 |

**모델을 부르지 않는다.** 유형 판정은 임계값 비교이고 총평은 블록 조합이라 생성이 끼지 않는다.

## 5. 문구 블록 시스템

런타임 AI 호출 없이 문장을 만드는 층이다. 조건 비교·해시 나머지·문자열 치환뿐이다.

### 5.1 재고

`ai/data/blocks/<슬롯>.json` 에 슬롯당 한 파일이다.

재고와 조합당 후보 수는 `uv run python scripts/check_blocks.py` 가 센다. **그 출력이
정본이고** 아래 표는 모양을 보여주기 위한 것이다.

| 슬롯 | 블록 수 | 조합당 후보 | 조건 키 |
|---|---|---|---|
| `daily_headline` | 46 | 3 | `vsIndex` × `mainMistake` (+ 폴백) |
| `trade_alias` | 29 | 4 | `tag` (7종 + 폴백) |
| `investor_type` | 7 | 1 | `profileLevel` (1~5 + 판정 불가 + 폴백) |
| `type_effect` | 16 | 6~9 | `axis` (+ 폴백) |
| `trait_title` | 21 | 2 | `traitItem` × `traitDirection` (+ 폴백) |
| `next_step` | 11 | 1 | `nextItem` × `nextDirection` (+ 폴백) |
| `actual_fallback` | 9 | 2 | `profileMatch` (+ 폴백) |
| `season_context` | 10 | 3 | `marketMove` (UP·FLAT·DOWN + 폴백) |

블록 문안을 만드는 프롬프트와 검수 체크리스트는
[`ai/prompts/report-blocks.md`](../../ai/prompts/report-blocks.md) 가 갖는다.

### 5.2 선택 6단계

```
extract → filter → pick → dedup → fallback → render
```

| 단계 | 규칙 |
|---|---|
| **extract** | 원자료를 조건 벡터로 줄인다. 판단이 들어가는 유일한 곳이다 (3.2 · 4.4) |
| **filter** | `when` 의 키가 **전부** 일치하는 블록만 남긴다. `when` 에 없는 키는 보지 않는다. `minCount` 미달, `requires` 값이 비면 그 블록만 뺀다 |
| **pick** | **무작위를 쓰지 않는다.** `sha256(account_id:season_day:slot) % 후보 수`. 같은 사용자가 다시 열면 같은 문장이 나오고, 같은 조건의 다른 사용자는 다른 변주를 받는다 |
| **dedup** | 직전 리포트에서 쓴 블록 ID 를 후보에서 뺀다. 빼고 나서 비면 빼지 않는다 — 중복이 빈 문장보다 낫다 |
| **fallback** | 슬롯마다 `when: {}` 인 기본 블록을 하나 둔다. 실제 조건에 맞는 블록이 있으면 폴백은 후보에서 빠진다 |
| **render** | 정의된 네 변수(`count`·`winCount`·`returnRate`·`rankRate`)만 치환한다. 없는 키는 예외를 던진다 — 조용히 비우면 "0회 중 회가" 가 사용자에게 나간다 |

### 5.3 별칭의 예외 규칙

- 그날 잘한 거래가 하나뿐이면 "유일한 정답", 아쉬운 거래가 하나뿐이면 "오늘의 유일한 실수" 를
  코드가 직접 붙인다.
- 단 `BEST_TRADE`·`WORST_TRADE` 는 정의상 하루에 하나씩이라 이 규칙에서 빼 둔다. 그러지 않으면
  그 둘의 전용 별칭이 영영 쓰이지 않는다.
- 한 리포트 안에서 이미 쓴 별칭은 다음 장면에서 뺀다. 시드만 다르게 해서는 겹침을 막지 못한다.

## 6. 헤드라인 LLM 생성

일일 헤드라인에만 쓴다. **블록을 대체하는 것이 아니라 위에 덧칠하는 층이다.**

### 6.1 무엇을 보내나

| 보낸다 | 보내지 않는다 |
|---|---|
| `vsIndex` 라벨 (예: "시장에 뒤졌다") | 종목명 |
| `mainMistake` 라벨 (예: "고점에서 사들인 자리") | 계정 ID·닉네임 |
| 체결 건수, 잘 맞은 자리 수, 아쉬운 자리 수 | 체결 원본·금액 |

게임 종목이 실제와 다른 임의의 이름이라, 이름을 넘기지 않으면 **익명화가 프롬프트 지침이 아니라
구조로 지켜진다.** 프롬프트 문안은 [`ai/prompts/daily-headline.md`](../../ai/prompts/daily-headline.md)
가 갖고, 코드는 값 채우기와 검사만 한다.

### 6.2 호출

| 항목 | 값 |
|---|---|
| 게이트웨이 | SSAFY GMS (`https://gms.ssafy.io/gmsapi/api.openai.com/v1`) — OpenAI `/chat/completions` 프록시 |
| 모델 | `gpt-5-mini` (기본). `gpt-5-nano` 는 목업 비교에서 문장이 깨지는 일이 있었다 |
| 파라미터 | `max_completion_tokens` 512 · `reasoning_effort` `minimal`. `temperature` 는 보내지 않는다 (gpt-5 계열이 거절) |
| 타임아웃 | 호출당 15초 |
| 동시 호출 | 8 (세마포어). 계좌 수만큼 부르므로 상한이 없으면 429 로 무너진다 |
| 재시도 | 408·429·5xx 에 한해 1초 뒤 한 번만. 무한히 물러서면 발표 시각을 넘긴다 |

100명이면 13배치가 순차로 돈다. 그 시간이 백엔드의 읽기 상한(4분) 안에 들어간다.

### 6.3 검사 — 사람이 검수하지 않고 바로 나간다

생성 문장은 네 가지를 지나야 한다. 하나라도 걸리면 **조용히 블록 문장으로 돌아간다.**

1. 길이 45자 이하 (블록 37개가 16~27자라, 넘으면 화면에서 한 줄을 벗어난다)
2. `니다.` 로 끝날 것 (마침표만 보면 "~평가된다" 같은 문어체 이탈이 통과한다)
3. 아라비아 숫자 없음 (수치는 지표 칩이 따로 보여준다)
4. 금지어 없음 — 실제 고유명사(코스피·나스닥·삼성·비트코인·코로나 등)와 투자 권유·훈계

문장을 감싸고 온 따옴표는 거르지 않고 벗긴다. 걸린 사유와 길이만 로그에 남기고 **생성 문장
원문은 남기지 않는다** — 어느 규칙이 얼마나 걸리는지 봐야 문안을 고칠 수 있기 때문이다.

### 6.4 켜고 끄기

`AI_LLM_API_KEY` 를 채우면 켜진다. 키가 없으면 꺼진 채로 뜨고 헤드라인은 전부 블록 문장이다.
`AI_LLM_ENABLED=true` 라고 **명시했는데 키가 없으면 기동에서 막는다** — 의도와 결과가 어긋난
상태로 조용히 돌아가지 않게 한다.

## 7. 실패 정책

| 실패 | 처리 |
|---|---|
| 한 계좌의 문구 조립 실패 | 그 계좌만 응답에서 빠진다. **나머지는 보낸다.** 원인은 로그에 남는다 |
| 헤드라인 생성 실패·검사 탈락 | 실패가 아니다. 그 자리에 블록 문장이 들어간다 |
| 게이트웨이 장애 | 한 번 재시도 후 포기. 전원이 블록 문장으로 나간다 |
| AI 응답 없음 | 백엔드가 두 번 부르고, 그래도 못 받으면 문구 자리를 비운 채 리포트를 연다 |
| 블록 파일 누락·치환값 없음 | 500. 반쪽 문장을 사용자에게 내보내지 않는다 |

한 명의 조립 실패로 100명의 리포트를 비울 이유가 없다는 것이 이 표의 요지다.

**요청 본문을 로그에 남기지 않는다.** 건수와 걸린 시간만 남긴다. API 키·프롬프트·생성 문장
원문도 남기지 않는다.

## 8. 설정값

환경변수 접두사는 `AI_` 로 고정한다 (모노레포에서 다른 컨텍스트와 충돌 방지). `.env` 는
커밋하지 않고, 키를 추가하면 `.env.example` 에 의미를 주석으로 남긴다.

| 키 | 기본값 | 비고 |
|---|---|---|
| `AI_ENV` | `local` | `local`·`dev`·`prod` |
| `AI_HOST` · `AI_PORT` | `0.0.0.0` · `8000` | |
| `AI_LOG_LEVEL` | `INFO` | |
| `AI_INTERNAL_API_KEY` | (빈값) | **`env != local` 에서 필수.** 없으면 기동 실패 |
| `AI_CORS_ALLOW_ORIGINS` | (빈값) | 비우면 미들웨어를 아예 붙이지 않는다. 내부 서비스의 기본값 |
| `AI_LLM_API_KEY` | (빈값) | GMS 키. 토큰만큼 크레딧이 차감된다. 로그·응답 어디에도 남기지 않는다 |
| `AI_LLM_ENABLED` | (빈값 = 키 유무로 결정) | `true` 인데 키가 없으면 기동 실패 |
| `AI_MODEL_DIR` | (빈값) | 로컬 모델 가중치 경로. 가중치는 커밋하지 않는다 |

환경과 무관한 값(`api_prefix`, LLM 모델·타임아웃·동시성)은 `app/core/config.py` 의
기본값으로 두고 외부화하지 않는다. 필요하면 같은 이름의 환경변수로 덮을 수 있다.

## 9. 성능과 용량

- 리포트는 **폐장 스냅샷**이다. 사용자가 열 때 만들지 않고 하루가 끝날 때 한 번 만들어 저장한다.
  조회 요청 수와 무관하다.
- 사용자 100명이면 하루 100건, 시즌 전체로 400건이다.
- 폐장 16:40 → 발표 17:00 사이 20분이 예산이다. 헤드라인 생성(동시 8, 13배치)이 그 안에서 끝난다.
- payload 는 계좌당 350~650B. 100명이면 한 요청이 수십 KB 수준이다.
- 블록 조립 자체는 조건 비교와 해시라 사실상 무비용이다.

## 10. 검증 수단

백엔드를 기다리지 않고 **payload → 판정 → 문장** 전체를 돌려 볼 수 있다. 목업 생성기가
`app/schemas/inbound.py` 로 자기 출력을 검증하므로, 계약이 바뀌면 목업이 먼저 깨진다.

| 명령 | 보는 것 |
|---|---|
| `uv run python scripts/preview_report.py --llm --api` | 목업 유저의 입력·판정·문장. `--api` 는 실제 엔드포인트를 지난다 (인증·계약·라우팅까지) |
| `uv run python scripts/check_blocks.py --spread 100` | 블록 재고와 조건별 후보 수 |
| `uv run python scripts/check_llm.py` | GMS 연결·생성·검사 (실제 호출이라 크레딧이 조금 든다) |
| `uv run python scripts/mock_data.py --users 30 --out mock.json` | 목업 payload 만 |
| `uv run pytest` | 자동 테스트 **696개 통과** (2026-09-14 기준) |

커밋 전에는 `uv run ruff format . && uv run ruff check . && uv run pytest` 세 개를 통과시킨다.
